## 1. 背景

W1 交付 `hooks`/`verify` 的**声明层**后，本波交付**兑现面**：hooks 物化到 13 宿主落点、`host verify` 物化校验、P0 门禁在宿主内真实生效（宿主触发 hook → 门禁拒绝脏提交/脏归档，而非仅 CLI 侧把关）——这是 SpecWave 与 Ruler/spec-kit 拉开差距的战略卖点。

**B5 的准确缺口（本轮复核修正 · 旧口径被 `--file` 证伪）**：**不是「外部表接不进来」** —— `host validate` / `apply` / `update` **早已接受 `--file PATH`**（`cli-host.ts:472/1140/1301`；`resolveValidateFile:438-441` 有 `fileArg` 即用、否则回包内默认），第三方今天就能用一张外部表接入自有 agent，无需改包发版。真正缺的是：① **catalog**（表不可发现 · 无版本/完整性声明）；② **用户级目录**（必须每次手传 `--file`，无法「装一次全局可用」）；③ **多表合并**（只能一张表，无法「内置 13 宿主 + 我的增量」组合）。

**第三方视角（本波硬要求 · 硬约束 12）**：B5 交付后须保证**新增一个非内置自定义 agent 全程不改 spec-wave 发版** —— 「写一张表 → `--file`（现状路径）或 catalog（B5 路径）→ 物化 + verify」闭环可用；任何要求「改 spec-wave 源码后重新发版才能接入」的设计一律视为 B5 未达成。

## 2. 目标

1. **hooks 物化**：按 W1 的「机制族」抽象（shell-hook / config-hook / 无 hook 降级）把 hooks 声明物化到 13 宿主落点。
2. **`host verify` 物化**：校验宿主侧已物化内容与声明一致，检出人为篡改。
3. **P0 门禁宿主内真生效**：宿主触发 hook → 门禁拒绝脏提交，留端到端证据。
4. **B5 插件机制**：catalog（可发现 + 版本/完整性声明）+ 用户级目录 `~/.spec-wave/hosts/` 自动加载 + 多表合并（内置 13 + 用户增量）。
5. **无 hook 宿主显式降级**：声明 hooks 但宿主无可用机制时，显式降级 L1+L2 且输出中可区分，**不得静默装作已进 L3**。

## 5. 设计

### 5.1 机制族抽象（而非逐宿主硬编码）

各宿主 hook 机制差异大且文档质量参差 ⇒ 按**机制族**归纳（起草轮三分：shell-hook / config-hook / 无 hook 降级），物化器按族实现，宿主声明所属族。具体族划分以 W2 task 复核各宿主文档后定稿。

### 5.2 `host verify` 语义

读取宿主侧已物化内容 ↔ 适配表声明逐项比对：一致 → 绿；被人为篡改/删除 → 报红点明落点。fail-closed：无法读取落点按红处理（或按族声明的降级口径），不得静默跳过。

### 5.3 B5 加载优先级与合并（草案 · task 定稿）

1. 内置表（包内 `mvp-hosts.yaml`）恒为基底。
2. 用户级目录 `~/.spec-wave/hosts/*.yaml` 自动加载为增量；`--file` 为当次显式覆盖/增量（优先级规则 task 定稿）。
3. **合并铁律**：用户表可**新增**宿主 id；**不得覆盖/篡改内置 13 宿主**（冲突 → 拒绝并点名 · 负向 fixture 固化）。
4. catalog 记录表来源/版本/完整性声明（格式随 W1 schema 延伸 · task 定稿）。

## 6. 方案对比（R2 摘要）

| 方案 | 结论 | 理由 |
|------|------|------|
| hooks 按机制族抽象 | **采纳** | 宿主机制差异大 · 文档质量参差 · 族抽象可测试可降级（PLAN W2 风险条） |
| hooks 逐宿主硬编码物化 | 弃选 | 13 套特判不可维护 · 新宿主接入又要求改码（违硬约束 12） |
| 无 hook 宿主显式降级留痕 | **采纳** | 不静默装 L3 · 对外口径受事实卡约束（硬约束 9） |
| 无 hook 宿主按「已实现 hooks」处理 | 弃选 | 虚报能力 · 对外文案失真 |
| 用户表合并 = 增量优先 + 内置不可覆盖 | **采纳** | 内置 13 宿主是 pins/验收锚点 · 被覆盖则真值面失守（负向 fixture） |
| 用户表合并 = 后到优先全覆盖 | 弃选 | 恶意/损坏表可静默顶替内置宿主（安全风险） |

## 7. 验收标准（必须自证，不接受「我改完了」）

1. **≥2 个真实宿主端到端演示**：hook 被宿主真实触发 → 门禁拒绝一次脏提交，留录屏/日志证据（入 `docs/harness/reviews/` 或 tracked 验收材料 · 硬约束 14）。
2. **`host verify` 双向**：对人为篡改的宿主落点报红、对合规报绿（负向/正向 fixture）。
3. **用户级目录不破坏内置**：负向 fixture —— 恶意/损坏的用户表**不得覆盖**内置 13 宿主（冲突拒绝点名）；正向 —— 增量宿主正常物化。
4. `pins check` 与 `host validate` 全绿。
5. **第三方自定义 agent e2e（硬要求）**：新造**不在内置 13 宿主之列**的宿主 id，仅凭一张用户表走通 `host apply --file`（现状路径）与 catalog 加载（B5 路径）**两条路**，且 `host verify` 对其生效 → **证明接入面不依赖改包发版**（硬约束 12）。
6. **无 hook 宿主降级留痕**：声明 hooks 但宿主无可用机制时，显式降级 L1+L2 且输出中**可区分**（快照断言）；不得静默装作已进 L3。
7. `npm run typecheck` 0 错 · `npm test` 全绿（含新增 e2e · 注意 E3 减负后的测试耗时预算）。
