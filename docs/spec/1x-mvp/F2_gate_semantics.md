## 1. 背景与目标

P0 门禁（`check` / `verify` / `gate-check` / `audit` + D5）已是产品差异化核心，但对外契约未成文对齐行业事实标准：阻断码、失败即阻断、分层强制。

**一句话目标**：把 **退出码 2 = 阻断**、**failClosed**、**分层强制** 写入 README/SPEC（及必要实现对齐），使 CI / Agent 可机械解读。

**完成态行为**

1. 文档明确：`2` = 门禁失败不放行；`1` = 非阻断类失败/用法错误（与现网族一致处保持，变更须 freeze）；`0` = 通过。  
2. `gate-check` / `verify` / `audit` 在 P0 失败路径 **failClosed**（失败即阻断，exit 2），禁止「失败仍 0」。  
3. D5（`test_strategy=required`）失败 = exit 2（1.5.0 起 WARN 过渡已移除——本 F 只确认文档与回归仍钉死）。  
4. 「分层强制」：至少在文档定义优先级（例：仓库门禁结论 > 本地跳过习惯）；1.x **不**引入 Cursor 式云下发四层配置引擎。

## 2. 范围

### 2.1 In

- README（中英）/ 仓根或系列 SPEC 的门禁语义专节  
- 必要时修正命令 help / 错误文案与退出码不一致处  
- 回归单测：P0 失败路径 exit 2；用法错误 exit 1（若现网如此）  
- 与 F1 联测：S2 拒写路径的退出码符合契约

### 2.2 非范围

- 不改命令名 / 不新增云仪表盘  
- 不实现宿主 hooks 桥接（仍是进程内机械判定）  
- 不重做 D5 探测白名单（除非发现与语义冲突的 bug）  
- 不把 UserStory §3.1 中疑似笔误「gate-check 失败即放行（退出码 1）」当作真值——**以高层架构 §6.4「gate-check 失败不放行 / 退出码 2」为准**

## 3. 方案要点（R2）

| 方案 | 要点 | 结论 |
|------|------|------|
| A. 文档契约 + 缺口补测 + 小改文案/退出码 | 最低风险对齐行业语义 | **推荐** |
| B. 大改退出码族（破坏消费者 CI） | 需 major；违背 1.x「不改产品形态」 | **弃选**（除非审计证明现网已全面错误） |
| C. 引入完整四层远程策略引擎 | 云/宿主绑定；越界 | **弃选** |
