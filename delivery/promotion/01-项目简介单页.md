# dsh-coding-kit · 项目简介

> **给 AI 编码过程加「可证明的纪律」——规范注入、机械门禁、过程轨留档，三件事在一次 `npx` 之内闭环。**

---

## 一句话定位

**dsh-coding-kit**（kit）是「**跨宿主规范分发器**」—— 把团队的 AI 编码纪律，从"建议性提示词"升级为"机械性门禁 + 留档可审计的过程轨"。**DSH 是首个宿主，不是唯一宿主**；1.x 收敛内部一致性，2.0 引入宿主适配表。

---

## 价值三段式

| 维度 | 内容 |
|------|------|
| **对外价值**（开发者） | 规范注入（Inform / Constrain）+ 机械门禁（Verify）+ 过程轨留档（Orchestrate），让编码过程**可追溯、可审计、可复现**。门禁判定独立于宿主进程，不被"提示词没生效"绕过。 |
| **对内价值**（维护者） | 获得"跨宿主规范分发器"的可扩展底座，规避宿主单点依赖；同时把分散在 4 份硬编码里的"永不覆写 S2"硬约束收敛为单一真值源，消除多入口维护的隐性成本。 |
| **差异化价值** | 五家 AI 编码规范标杆（Claude Code / Cursor / spec-kit / Ruler / AWS Kiro）中**无任何一家**同时提供「**门禁 + 过程轨留档 + 角色分帽（ICVO + hat 00/10/20/30/40）**」的等价物——这是 kit 不被 Ruler 类工具替代的根因，也是护城河。 |

---

## 双入口

- **插件面**（DSH 宿主内）— `apply_coding_standards` / `init_coding_kit`
- **CLI 面**（任何仓库）— `npx dsh-coding-kit check / verify / gate-check / audit`

> **P0 门禁**：判定走进程内机械逻辑（退出码 2 = 阻断），不依赖宿主是否执行了 hook。Skills 覆盖不了的事，门禁覆盖得了。

## 适用场景

- ✅ 团队希望把"AI 编码规范"从"提示词"升级为"可机械阻断 + 可审计"
- ✅ 现有 `AGENTS.md` / `CLAUDE.md` 散落、版本不一致、没人守
- ✅ 需要在 CI 流程里加可解释的"门禁"而非黑盒 Agent
- ✅ 想要"跨宿主"的规范分发能力，但不愿被任一 IDE 锁死

## 不适用

- ❌ 需要云端协作面板（kit 是**纯本地 CLI + npm 包**，零云资源）
- ❌ 需要订阅制商业服务（kit 是 MIT 开源，**当前不做商业化**）
- ❌ 自研 IDE 的端到端体验（这是 AWS Kiro 的路线，与 kit 零云约束冲突）
