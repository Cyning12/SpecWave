# 给 AI 编码加纪律：dsh-coding-kit 从 1.x 到 2.0 的演进路线

> 这是一份给技术社区和潜在用户看的"我们做了什么、为什么这么做、下一步去哪"。

---

## 引子：当规范变成 prompt 而不是 gate

过去两年，`AGENTS.md` / `CLAUDE.md` / `.cursorrules` 几乎成了"团队 AI 编码规范"的事实标准。截至 2025 年 8 月，`AGENTS.md` 已被 **60,000+ 开源项目**采用；2025 年 12 月，它与 Anthropic 的 MCP、Block 的 goose 一同被捐入 Linux Foundation 新设的 **Agentic AI Foundation（AAIF）**——AWS、Anthropic、Block、Bloomberg、Cloudflare、Google、Microsoft、OpenAI 都是白金成员。

但凡是真正用过的团队，都会撞上同一道墙：

> **规范是"提示词"，不是"门禁"**。

`AGENTS.md` 写得再清楚，模型"没看到"也不会报错；`CLAUDE.md` 写得再完整，宿主把它当请求而不是保证；"请遵循规范"这句话在被违反时**不会**让管道失败。

`dsh-coding-kit`（kit）想做的事很简单：**把规范从"请求"升级为"门禁"**——而且这个门禁**不依赖宿主是否执行了 hook**。

## 我们做了 5 家标杆的盘点，结论是什么

为了确认 kit 的方向不是凭空造轮子，我们做了行业调研，对比了 5 个最有可比性的工具（加权评分 1–5，权重和为 1.00）：

| 工具 | 加权总分 | 它做得最好的事 | 它没做的事 |
|------|---------|---------------|-----------|
| **Ruler** | 4.40 | 单一规范源 → 32 个 agent 原生配置位 | **不做门禁** |
| **GitHub spec-kit** | 4.35 | 模板四层优先级、过程产物入仓可审 | 门禁是**流程性**的（不验证代码能跑） |
| **Claude Code** | 3.90 | 门禁语义（退出码 2 / `permissionDecision: deny`） | 绑定宿主 |
| **Cursor** | 3.40 | 四层配置优先级、`failClosed` 失败即阻断 | 绑定 IDE |
| **AWS Kiro** | 2.55 | 规格驱动 + 完整迁移治理范式 | 绑定 AWS/Bedrock、自成 IDE 闭环 |

调研得出的两条关键事实：

1. **「规范注入」这一层已经标准化**（`AGENTS.md` + Agent Skills + 基金会中立治理），**赛道竞争已从"能不能注入"转移到"注入后是否确定执行、产物是否留档可审"**。
2. **Ruler 拿了最高的场景契合度 5/5，但它选择只做注入、不做门禁**。这是 kit 的空档：门禁 + 过程轨留档 + 角色分帽——五家标杆中无任何一家同时提供这三件事的等价物。

这正是 kit 的护城河。

## kit 怎么做：ICVO + hat + P0 门禁

kit 的方法论内核叫 **ICVO**——四个阶段、每个阶段都有落点：

| 阶段 | 含义 | kit 落点 |
|------|------|---------|
| **Inform** | 注入规范与上下文 | `apply_coding_standards` 插件工具、`assets/` 适配器 |
| **Constrain** | 约束产物形态与过程边界 | hat 帽制（00/10/20/30/40）、S2 永不覆写硬约束 |
| **Verify** | 机械验证 | `check` / `verify` / `gate-check` / `audit` P0 门禁，**退出码 2 直接阻断** |
| **Orchestrate** | 过程留档 | `docs/tasks/` + `docs/harness/reviews/` + `docs/harness/invokes/by-task/`（S2 永不覆写） |

**关键差异**：kit 的 P0 门禁判定走**进程内机械逻辑**，不依赖宿主 hook 是否被触发。这意味着无论 `apply_coding_standards` 有没有被调用到，CI 里的 `npx dsh-coding-kit verify` 都会按"硬约束"判定——退出码 2 让管道失败，不靠"模型是否听话"。

**角色帽制（hat）**是另一个差异化点。kit 不假定"AI 是一回事"——它把执行能力分成 5 档：

- `00`：delegate-only（只下发，不能直接执行）
- `10` / `20` / `30` / `40`：execute（按帽执行，含日志、含限制）

这与 ICVO 一起，让 kit 把"纪律"这件事变成可配置、可审计、可分帽的工程对象，而不是一句"请遵循"。

## 1.x 路线：先把内部一致性收敛完（**DONE**）

`dsh-coding-kit` **1.x MVP 已于 1.11.0 完成**，**1.12.0 为收口 minor**（见 [`docs/roadmap/PLAN_post_1.11_zh.md`](../../docs/roadmap/PLAN_post_1.11_zh.md)）。1.x 阶段不做新形态，做**纯内部重构 + 文档工程**：

| ID | Feature | 解决什么 | 状态 |
|----|---------|---------|------|
| F1 | S2 过程域真源统一 | 消除多份互不相同的硬编码（"永不覆写 S2"） | ✅ 1.11.0 |
| F2 | P0 门禁语义对齐 | `check` / `verify` / `gate-check` / `audit`，退出码 2 = 阻断 | ✅ 1.11.0 |
| F3 | 旧产品线 `@cyning/harness` 迁移时间表 | EOS 提案日历 + 迁移指南（deprecate **仅人**） | ✅ 文档 · 待 `HG-EOS-DATE` |
| F4 | `.coding-kit` 写根 + legacy 只读 | 新落盘统一；旧目录不删 | ✅ 1.11.0 |
| F5 | 版本钉方案 B | ontology / discipline / README；SPEC.md 为 archived epic | ✅ 1.11.0 |
| 收口 | 1.12 C*/O*/P6-prep | 测稳 · 本体论浅落地 · 宿主落点清单 | ✅ 1.12.0（待人 publish） |

> **为什么 1.x 不直接做"跨宿主分发"？** 因为 2.0 引入适配表之前，如果 1.x 自己的真值源还是分裂的，那"跨宿主"等于把分裂复制到 N 个宿主。**先把地基平整**——现已完成。

## 2.0 路线：跨宿主规范分发器

2.0 阶段，kit 演化为「**跨宿主规范分发器**」——一份规范源，自动落到多个宿主的原生配置位：

```
.ruler/（未来：kit 单一规范源）
    ↓
    ├── AGENTS.md        （AGENTS.md 规范，60,000+ 项目采用，基金会中立治理）
    ├── CLAUDE.md        （Claude Code）
    ├── .cursor/rules/   （Cursor）
    ├── .github/copilot-instructions.md   （GitHub Copilot）
    ├── .kiro/steering/  （Kiro）
    ├── .codex/          （OpenAI Codex）
    └── ...（32+ 宿主）
```

关键事实：`AGENTS.md` 是行业已收拢的**跨宿主公分母**。Ruler 32 个目标中**过半已经收敛为输出同一个 `AGENTS.md`**，这意味着"声明式适配表 + 单一规范源"在工程上已经跑通。kit 2.0 不是发明这个范式，是把它与**门禁 + 过程轨留档**绑在一起。

> **DSH 是首个宿主，不是唯一宿主**——这是我们对 1.x MVP 路线的定性。

## 迁移治理：@cyning/harness 怎么办

借鉴 AWS Kiro 的迁移治理范式（不是它的产品形态）：

| 步骤 | 借鉴 Kiro 的做法 | kit 1.x 落地 |
|------|-----------------|-------------|
| EOS 日 | 公开给定（Kiro 给 2027-04-30） | 维护者拍板，1.x MVP 阶段发布 |
| 新注册截止 | 早于 EOS 日（Kiro 2026-05-15） | 同步策略 |
| 多渠道保留 | 四个 IDE 市场保留插件 + 挂废弃公告 | npm 侧 `npm deprecate` + 仓库 MIGRATION 文档 |
| 迁移指南 | 按渠道分别给 | kit 1.x 给 `.cyning-harness → kit` 一份指南 |
| 过渡期补丁 | 续推关键修复 6–12 个月 | 同上 |

工具都现成（`npm deprecate` 是内置命令），缺的只是**时间表**与**文档投入**。
