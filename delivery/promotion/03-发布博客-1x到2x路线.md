# 给 AI 编码加纪律：从 SpecGate 到 SpecWave 的 1.x → 2.1 演进

> 这是一份给技术社区和潜在用户看的"我们做了什么、为什么这么做、下一步去哪"。

---

## 引子：当规范变成 prompt 而不是 gate

过去两年，`AGENTS.md` / `CLAUDE.md` / `.cursorrules` 几乎成了"团队 AI 编码规范"的事实标准，并有基金会中立治理背书（`AGENTS.md` 与 Agent Skills 已被纳入中立治理轨道）。

但凡是真正用过的团队，都会撞上同一道墙：

> **规范是"提示词"，不是"门禁"。**

`AGENTS.md` 写得再清楚，模型"没看到"也不会报错；`CLAUDE.md` 写得再完整，宿主把它当请求而不是保证；"请遵循规范"这句话在被违反时**不会**让管道失败。

SpecWave 想做的事很简单：**把规范从"请求"升级为"门禁"**——而且这个门禁**不依赖宿主是否执行了 hook**。（SpecWave 的前身是 dsh-coding-kit 与更早的 SpecGate；现在三者统一为一个名字 **SpecWave**，npm 包 `spec-wave@2.1.3`。）

## 我们做了 5 家标杆的盘点，结论是什么

为了确认方向不是凭空造轮子，我们做了行业调研，对比了 5 个最有可比性的工具（加权评分 1–5，权重和为 1.00）：

| 工具 | 加权总分 | 它做得最好的事 | 它没做的事 |
|------|---------|---------------|-----------|
| **Ruler** | 4.40 | 单一规范源 → 32 个 agent 原生配置位 | **不做门禁** |
| **GitHub spec-kit** | 4.35 | 模板四层优先级、过程产物入仓可审 | 门禁是**流程性**的（不验证代码能跑） |
| **Claude Code** | 3.90 | 门禁语义（退出码 2 / `permissionDecision: deny`） | 绑定宿主 |
| **Cursor** | 3.40 | 四层配置优先级、`failClosed` 失败即阻断 | 绑定 IDE |
| **AWS Kiro** | 2.55 | 规格驱动 + 完整迁移治理范式 | 绑定 AWS/Bedrock、自成 IDE 闭环 |

> **本方调研（自评）**：上表加权评分出自 `delivery/research_report.md`，属**我们自己的调研**，并非第三方权威评测；SpecWave 在该表中是差异化列、**未给总分**，不存在"SpecWave 总分第一"的说法。

调研得出的两条关键事实：

1. **「规范注入」这一层已经标准化**（`AGENTS.md` + Agent Skills + 基金会中立治理），**赛道竞争已从"能不能注入"转移到"注入后是否确定执行、产物是否留档可审"**。
2. **Ruler 拿了最高的场景契合度（5/5），但它选择只做注入、不做门禁**。这是 SpecWave 的空档：门禁 + 过程轨留档 + 角色分帽——**五家标杆中，没有任何一家同时提供这三件事的等价物**。

这正是 SpecWave 的护城河（也是唯一允许这样表述的版本）。

## SpecWave 怎么做：ICVO + hat + P0 门禁

SpecWave 的方法论内核叫 **ICVO**——四个阶段、每个阶段都有落点：

| 阶段 | 含义 | SpecWave 落点 |
|------|------|--------------|
| **Inform** | 注入规范与上下文 | `apply_coding_standards` 插件工具、`assets/` 适配器 |
| **Constrain** | 约束产物形态与过程边界 | hat 帽制（starter 4 帽 + extended 4 帽）、S2 永不覆写硬约束 |
| **Verify** | 机械验证 | `check` / `verify` / `gate-check` / `audit` P0 门禁，**退出码 2 直接阻断** |
| **Orchestrate** | 过程留档 | `docs/tasks/` + `docs/harness/reviews/` + `docs/harness/invokes/by-task/`（S2 永不覆写） |

**关键差异**：SpecWave 的 P0 门禁判定走**进程内机械逻辑**，不依赖宿主 hook 是否被触发。这意味着无论 `apply_coding_standards` 有没有被调用到，CI 里的 `npx spec-wave verify` 都会按"硬约束"判定——退出码 2 让管道失败，不靠"模型是否听话"。

**角色帽制（hat）**是另一个差异化点。SpecWave 不假定"AI 是一回事"——它把执行能力分成 **8 顶帽，分两组**：

- **starter 组（4 顶，落地执行与自检）**：`10-task` · `20-task-audit` · `30-execute-code` · `40-self-check`
- **extended 组（4 顶，编排与独立复核）**：`00-orchestrator` · `10-spec` · `20-spec-audit` · `50-independent-reinspect`

配合 4 道人闸（`HG-TASK-DRAFT` / `HG-SPEC-SIGNOFF` / `HG-AUDIT-R1` / `HG-RELEASE`），让"纪律"变成可配置、可审计、可分帽的工程对象，而不是一句"请遵循"。

## 1.x 路线：先把内部一致性收敛完（**DONE**）

SpecWave **1.x MVP 已于 1.11.0 完成**，**1.12.0 为收口 minor**（规划参见已归档的 [`docs/roadmap/PLAN_post_1.11_zh.md`](../../docs/roadmap/PLAN_post_1.11_zh.md)）。1.x 阶段不做新形态，做**纯内部重构 + 文档工程**：

| ID | Feature | 解决什么 | 状态 |
|----|---------|---------|------|
| F1 | S2 过程域真源统一 | 消除多份互不相同的硬编码（"永不覆写 S2"） | ✅ 1.11.0 |
| F2 | P0 门禁语义对齐 | `check` / `verify` / `gate-check` / `audit`，退出码 2 = 阻断 | ✅ 1.11.0 |
| F3 | 旧产品线 `@cyning/harness` 迁移时间表 | EOS 日历已公布 + deprecate 已执行 | ✅ 文档 · **已 deprecate** |
| F4 | `.coding-kit` 写根 + legacy 只读 | 新落盘统一；旧目录不删 | ✅ 1.11.0 |
| F5 | 版本钉方案 B | ontology / discipline / README；SPEC.md 为 archived epic | ✅ 1.11.0 |
| 收口 | 1.12 本体论浅落地（O1–O3）· 宿主落点声明 prep | 测稳 · 本体论浅落地 · 宿主落点声明 | ✅ **1.12.0 published** |

> **为什么 1.x 不直接做"跨宿主分发"？** 因为 2.0.0 引入适配表之前，如果 1.x 自己的真值源还是分裂的，那"跨宿主"等于把分裂复制到 N 个宿主。**先把地基平整**——现已完成。

## 2.x 已交付：跨宿主规范分发器

2.0.0 起，SpecWave 演化为「**跨宿主规范分发器**」——一份规范源，通过声明式适配表自动落到多个宿主的原生配置位。这不是路线图上的"未来规划"，而是**已经逐版交付**的事实：

- **2.0.0 · 宿主适配（F6）**：新增 `host validate` / `host apply` / `host update`；Cursor + Claude Code + DSH **三角物化**；契约嗅探 U-01（适配表 version 与可选 peer 不匹配 → exit 2 零写入）。
- **2.1.0 · Skills + 编排 parity**：补齐多平台 skills 与 commands——Claude `/kit:verb`（`/kit:` 命名空间）、DSH `.dsh/skills/kit-*`（`/` 可发现，无 `.dsh/commands/`），并引入 `--profile expanded` 物化 `kit-hat-*` 薄壳。
- **2.1.1 · 安装/更新 UX**：sticky 选型（`.coding-kit/host-tools.json` 记住 `host_ids` + `profile`，dry-run 不写）；`--tools`（`LIST` / `all` / `none`）；`init` 交互询问 IDE/宿主——**对齐 OpenSpec 的 `init --tools` 范式**。
- **2.1.2 · 改名收口**：身份面统一为 **SpecWave**，切断以废弃中间包为终点的链式叙事；建立 **2.1.2+ 起 tag↔npm 同 commit 的可溯源绑定**。
- **2.1.3 · 溯源自动化**：`release-tag-identity` 测试校验 `git tag v<version>` 与 `package.json` 身份一致；README 双语对齐；负向断言防改名后"恒真"。

**真实的四宿主 `host apply` 落点（profile `core`）：**

| Host | `host apply` 落点（profile `core`） |
|------|-------------------------------------|
| **Cursor** | `.cursor/rules/*.mdc` · `.cursor/commands/kit-*.md` · `.cursor/skills/` |
| **Claude Code** | `CLAUDE.md` 产品标记块 · `.claude/commands/kit/<verb>.md` → **`/kit:verb`** · `.claude/skills/` |
| **DSH** | `.dsh/skills/`（hat skills **+** 编排 `kit-*`，`/` 可发现；**无** `.dsh/commands/`） |
| **agents** | `AGENTS.md` 片段 · `.agents/skills/` |

> **重要边界**：安装 npm 包**不会**自动物化 IDE 文件（无 postinstall）。必须显式跑 `init --tools` 或 `host apply` 才会落地上述文件。

**纪律覆盖度：主动公开未接线项（这是卖点，不是缺陷）。** SpecWave 不宣称"100% 机械强制"。跑 `npx spec-wave discipline show` 即可看到自己在 2.1.3 下的真实覆盖：30 条 statements 中 **mechanical 11 / partial 7 / prompt-only 9 / not_wired 3**。我们把未接线项直接摆出来，而不是把它藏成"宣称即能力"——这是与多数同类工具的真实差异。

**质量事实（2026-09-11 实测）**：**406 用例 · 54 文件 · 48.7s 全通过**；typecheck **0 错误 0 警告**；运行时依赖**仅 `js-yaml` 1 个**；CI 跑 Node 22.x + 24.x 矩阵（`npm ci → typecheck → test → build → test:lib`）。

## 迁移治理：@cyning/harness 与 dsh-coding-kit 怎么办

借鉴 AWS Kiro 的迁移治理范式（不是它的产品形态）：

| 步骤 | 借鉴 Kiro 的做法 | SpecWave 落地 |
|------|-----------------|--------------|
| EOS 日 | 公开给定 | 维护者拍板，1.x MVP 阶段发布 |
| 新注册截止 | 早于 EOS 日 | 同步策略 |
| 多渠道保留 | 四个 IDE 市场保留插件 + 挂废弃公告 | npm 侧 `npm deprecate` + 仓库 MIGRATION 文档 |
| 迁移指南 | 按渠道分别给 | 给 `.cyning-harness → SpecWave` 与 `dsh-coding-kit → spec-wave` 两份指南 |
| 过渡期补丁 | 续推关键修复 6–12 个月 | 同上 |

**迁移终点统一为 `spec-wave`**：`@cyning/harness` 与 `dsh-coding-kit` **两者均已 `deprecate`**，旧包文案均指向 `spec-wave`；同名过渡 bin `specgate` / `dsh-coding-kit` 仍可用，但入口名已是 **SpecWave**。

工具都现成（`npm deprecate` 是内置命令），缺的只是**时间表**与**文档投入**。
